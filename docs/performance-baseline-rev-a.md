## `pg_stat_statements` — filtrert «app-domene» snapshot

**Formål:** Begrens støy fra platform (WAL, `pg_timezone_names`, PostgREST schema-cache, ren auth-metadata) og vis statements som refererer kjernepublic-tabeller.

**Filter:** DML-start (`select` / `insert` / `update` / `delete` / `with`) + tekst inneholder minst én av: `public.orders`, `public.profiles`, `public.day_choices`, `public.agreements`, `public.audit_log`, `public.company_memberships`, `public.company_locations`, `public.company_current_agreement`, `public.kitchen_batch`, `public.delivery_batches`, `public.outbox`, `public.driver_runs`, `public.standing_orders`. Ekskluderer åpenbar DDL (`alter table`, `create table`, `drop `).

**Konklusjon — signal-styrke:** **Lav.** Maks observert `calls` er **5** (ofte **2–5**) — konsistent med lite prod-trafikk og sub-skala data. Nyttig som arkivert referanse, ikke som bevis for flaskehalser under last.

## What this proves — and what it does not

### PROVES

- Faktisk schema- og relasjonsstørrelse (snapshot) for `public` top-tabeller.
- Faktisk seq_scan vs idx_scan-profil for tabeller med `n_live_tup > 100` (sub-skala).
- Faktiske Supabase performance-advarsler (full liste over — severity + regel + berørt tabell + lenket remediation).
- At `pg_stat_statements` kan filtreres mot kjernetabeller; med dagens trafikk er **kalltellingene** små.
- Grunnlag for videre arbeid i kode → DB (`hot-paths.md`, `performance-p-backlog.md`).

### DOES NOT PROVE

- 50K-firma skala-ytelse eller planner-valg ved svært store datasett.
- Connection pool- eller Auth-connection-grenser under ekte samtidighet.
- Cache-/cold-start-effekt i Next/serverless eller CDN.
- Concurrent-write contention (locks, deadlocks, hot rows).
- p95/p99 latency under definert last (ingen lasttest i Rev A).
